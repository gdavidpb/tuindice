# Local E2E Reference

## Architecture

- E2E scenarios are typed Kotlin data (`scenarios/`), interpreted by `scenariokit/` and performed by one native driver per
  platform: UI Automator out of process on Android (`scenariorunner/`), XCUITest on iOS (`iosApp/UITests/`). There is no
  separate runner or YAML flow: a behavior is covered by a scenario in the catalog or by a documented disposition.
- The harness in `e2e/scripts/` runs the scenarios one by one, resets the app between them, accumulates results per
  fingerprint and publishes the evidence. `e2e/README.md` is the operating manual.
- A driver only touches the screen. Anything a scenario needs from the app at launch comes through launch arguments
  (`maincore/.../debug/DebugLaunchArguments.kt`: session seed, section, coachmarks, fixed clock, network, animations).
- Platform edges no scenario can drive (OS hand-offs, secure-storage states) are recorded in `e2e/platform/<platform>/*.md`
  and in `ActionDispositions.kt`, with what covers them elsewhere (host and UI tests).

## Root Layout

- `scenariokit/`: step model, DSL (`scenario(...) { tap(...); waitVisible(...) }`), interpreter, driver contract and codec.
  No project dependencies.
- `scenarios/src/commonMain/.../scenarios/`: `catalog/` (one `<Module>Scenarios.kt` per module, `E2eCatalog.kt`,
  `ActionDispositions.kt`, `PlatformBranchBudget.kt`), `fixture/` (`E2eAccounts.kt`,
  `E2eFixtures.kt`, `Copy.kt`, `Start.kt`) and `shared/` (`SignInSteps.kt` and other step groups).
- `scenarios/src/androidHostTest/`: the rules, as host tests (`CatalogShapeTest`, `ModuleCatalogTest`, `CatalogTagsTest`,
  `CatalogStartTest`, `CatalogRulesTest`, `CatalogContentRulesTest`, `CatalogBudgetTest`, `ActionCoverageTest`,
  `AccountFixturesTest`, `AccountSessionFixturesTest`, `CopyTest`, `EntityFixturesTest`, `MockContractTest`,
  `RetryOrderMocksTest`, `LaunchArgsParityTest`, `TestInputsDeclaredTest`, `CatalogExportTest` and others).
- `e2e/catalog/scenarios.json` and `iosApp/UITests/Generated/ScenarioTests.generated.swift`: generated by the host tests,
  copied by `./gradlew syncE2eArtifacts`, versioned, and checked by `verifyE2eArtifactsFresh`.
- `e2e/scripts/`, `e2e/toolchain/`, `e2e/tools/`, `e2e/platform/`: harness, device locks, diagnostics and verifiers, edge notes.
- `testkit/e2e/`: `selector-policy.md` and `fixture-contract.md`, the reusable QA policy.
- `mocks/`: the WireMock runtime (mappings, bodies, base states, transformers).

## E2E Scope Gate

At the start of every module change, classify whether local E2E is in scope. It is in scope when the change touches any of:

- user-visible behavior, state, copy, empty/loading/failed/retry branches, or screen acceptance criteria
- navigation destinations, back results, top-level tabs, dialogs, deep links, or app startup/reset behavior
- presentation `Action`s, especially added/removed/renamed user actions or actions reclassified as internal/platform-edge
- `Modifier.testTag`, accessibility identifiers, selectors, or UI structure used by existing scenarios
- local backend contracts, WireMock mappings/bodies, fixture values, scenario state, debug URLs, or launch arguments
- platform hand-offs such as browser, file/PDF opener, camera/photo picker, permissions, share sheet, mail, store, or external intents

When E2E is in scope, include the scenarios and every required supporting artifact in the same change. Do not update only
app code and leave E2E as a follow-up. If E2E is out of scope, be ready to state the internal-only reason.

## What A New Module Adds

1. **`*UiTags`.** An `object <Module>UiTags` in `<module>/src/commonMain/.../ui/` with `const val` tags (and builder
   functions with a stable suffix for dynamic ones), put on the composables with `Modifier.testTag`. Existing examples:
   `AboutUiTags`, `AuthUiTags`, `SummaryUiTags`, `MaincoreUiTags`. `CatalogTagsTest` reads every `*UiTags.kt` under a
   module's `src/commonMain`, so nothing is registered; a builder template needs a non-empty literal prefix.
2. **Dependency of `:scenarios`.** Add `implementation(project(":<module>"))` to `scenarios/build.gradle.kts` and the
   module to the `scenarios=` line of `scripts/module-graph.txt`; run `./gradlew verifyModuleGraph`.
3. **Scenarios.** `scenarios/.../catalog/<Module>Scenarios.kt` (capitalized module name) declaring
   `val <module>Scenarios: List<Scenario>`, with ids `<module>-<name>` (`[a-z0-9-]+`), and one entry
   `"<module>" to <module>Scenarios` in `E2eCatalog.byModule`. A product module needs at least one scenario tagged `smoke`
   (`CatalogShapeTest`). A scenario declares its own start: `Start.Seeded(E2eAccounts.<Account>, section = ...)` or
   `Start.Clean()`; only the allowlisted sign-in scenarios type a credential, through `signInThroughUi`.
4. **Action coverage (`ActionDispositions`).** Every action of every `presentation/contract/*.kt` is either named in the
   `covers("<module>.<Contract>.<Action>")` of a scenario that fires it, or listed in `ActionDispositions.all` as
   `Internal` (the machine fires it, no user does), `PlatformEdge` (an OS hand-off no scenario can carry out) or `Pending`
   (a user action nobody has covered yet, visible debt), each with its reason. Never both (`ActionCoverageTest`); the
   counts per kind are fixed in that test, so adding a disposition means updating them. A module whose actions belong
   to another scenario module maps it in `ScenarioModuleOf.kt` (`wizard` actions are `coachmarks` scenarios).
5. **Accounts and fixtures.** A new credential goes in `fixture/E2eAccounts.kt` (and its `all` list) with the login mapping
   under `mocks/mappings/login/` that accepts it and the session values of that mapping; `AccountFixturesTest` and
   `AccountSessionFixturesTest` check them (update the account count in the first). A seeded account needs a sync stub
   (`CatalogContentRulesTest`). Texts the scenarios assert go in `fixture/Copy.kt` bound to a string resource, mock data,
   a launch argument or a stated derivation; ids and values in `fixture/E2eFixtures.kt` with the files that declare them.
6. **Mocks.** Backend behavior the scenarios need goes in `mocks/mappings/<domain>/` and `mocks/__files/<domain>/`; a new
   stateful transformer needs a reset path in `BackendEngine.resetPaths` (`MockContractTest`).
7. **Branches per platform.** An `onPlatform(...)` branch needs its count in `PlatformBranchBudget` (exact, owner's
   agreement to raise it); `back()` is Android only.
8. **Edge notes.** A platform edge gets a note under `e2e/platform/android/` or `e2e/platform/ios/` and a `PlatformEdge`
   disposition.
9. **Generate and verify.** `./gradlew syncE2eArtifacts verifyE2eContract`; commit the two generated files.

## Frontend Change Rules

- When adding or changing a user-visible flow, add or update the scenario in the catalog of its module, in the same
  change, with the actions it fires in `covers`.
- When changing a presentation `Action` in `commonMain`, `ActionCoverageTest` tells you which scenario or disposition
  to update: cover it, disposition it with a reason, or rename it where it is named.
- Prefer stable selectors based on `Modifier.testTag` through `*UiTags`; avoid text-only selectors for dynamic,
  translated, formatted, or duplicated labels. A text query comes from `Copy` or `E2eFixtures`.
- Add, preserve, or rename test tags and accessibility identifiers together with the scenario that needs them. Keep Android
  test tags visible to the driver through `testTagsAsResourceId` in the Android host.
- If a scenario depends on backend behavior, update WireMock mappings and response bodies under `mocks/` with the app
  change, and the fixture values in `scenarios/.../fixture/`.
- Write steps the way a user acts: one `enterText` per value (the interpreter re-reads the field and fails on a
  mismatch), one `tap` per control (a tap waits for the target to be visible and enabled), waits for the next
  target and never for a time. No retries, no longer timeouts, no `ifVisible` to tolerate a flaky step; named timeouts
  only (`Within.Assert`, `Action`, `Wait`, `Long`, `Sync`).
- If the edge cannot be driven, add the `PlatformEdge` disposition and the note under `e2e/platform/`.

## Local Validation

- Always run `./gradlew verifyE2eContract` after editing scenarios, fixtures, selectors, mocks or E2E docs; it includes
  the `:scenariokit` and `:scenarios` host tests, `verifyE2eArtifactsFresh`, `verifyE2eHarness` and
  `verifyLaunchArgumentContract`.
- After changing a scenario, run `./gradlew syncE2eArtifacts` first and commit the regenerated catalog JSON and Swift.
- To see a scenario work on a device, run it in diagnostic mode (it publishes nothing):
  `python3 e2e/scripts/shared/e2e.py run --platform all --mode diagnose --scenario <id>`, or
  `E2E_SCENARIOS=<id> ./gradlew e2eAndroid` / `e2eIos`. Report a platform you could not run as unverified.
- Evidence (`./gradlew e2eEvidence`) belongs to the certification skill (`.codex/skills/certify-tuindice-pr/`), not to a
  module change.
- Changes under `e2e/scripts/**`, `scenariokit/src/commonMain`, `scenarios/src/commonMain`, `mocks/` or the app sources
  change the E2E fingerprint, so they invalidate the evidence of the platform they touch; comments in those files count.

## Local Backend And Debug URLs

- E2E runs use one WireMock per platform: Android `http://10.0.2.2:18626/` (the emulator's alias of the host) and iOS
  `http://localhost:18627/`; the harness starts it and keeps its log in the run directory. Android fixes the base URL at build
  time (`-Ptuindice.apiBaseUrl`); iOS receives `TUINDICE_E2E_API_BASE_URL` and `TUINDICE_E2E_WEB_BASE_URL` from the driver.
- Debug bundle id `com.gdavidpb.tuindice.debug`; the iOS host builds with `iosApp/scripts/ci-build-ios-host.sh`.
