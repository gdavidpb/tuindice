# Spike: Formal state machine behind MVI (KStateMachine on SignIn)

Goal: validate that the implicit MVI mutations can be reified as a formal state machine —
transitions as first-class, enumerable entities with validity rules, telemetry, and diagram
export — without touching the screen contract, the UI, or navigation.

## What was built

- `base/presentation/statemachine/StateMachineViewModel.kt`: drop-in sibling of
  `BaseViewModel` with the same public surface (`state`, `effect`, `sendAction`) and the same
  automatic telemetry (`ScreenView`, `Action`, `State` with name-dedup, `Effect`). Internally,
  a single machine-loop coroutine consumes a FIFO channel of machine events (user actions
  mapped 1:1 plus internal events), processes them through a KStateMachine instance, and
  publishes two new events: `AppEvent.Transition(from, event, to)` on `PROCESSED` and
  `AppEvent.InvalidTransition(from, event)` on `IGNORED`.
- `auth/presentation/machine/SignInMachineEvent.kt`: machine alphabet = the 7 user actions
  plus the internal results `SignInSucceeded` / `SignInFailed(error)`.
- `SignInViewModel` rewritten on top of the machine. The 7 SignIn `ActionProcessor`s remain
  compiled and registered (rollback/reference) but are no longer used by the ViewModel.

## The machine (generated by `machine_exportsDeclaredTransitionsToMermaid`)

```mermaid
stateDiagram-v2
state sign_in_StateMachine {
    state idle
    state logging_in

    [*] --> idle
    idle --> idle : SetUsbId
    idle --> idle : SetPassword
    idle --> idle : TogglePasswordVisibility
    idle --> logging_in : ClickSignIn
    logging_in --> logging_in : SignInSucceeded
    logging_in --> idle : SignInFailed
    sign_in_StateMachine --> sign_in_StateMachine : ClickTermsAndConditions
    sign_in_StateMachine --> sign_in_StateMachine : ClickPrivacyPolicy
    sign_in_StateMachine --> sign_in_StateMachine : SetUsageDataCollectionEnabled
}
```

Machine-level self-loops are transitions valid from **any** state (hierarchical resolution),
matching today's unguarded behavior for terms/privacy/consent — now declared instead of
accidental.

## Semantics decided in this spike

- Formal state = the sealed `State` class; payload lives in the instance. `Content`-style
  flags do not multiply the state space.
- Inputs = user actions + internal events (use-case results). Launching the use case is an
  output of `idle × ClickSignIn → logging_in`; its result re-enters the loop as an event.
  `UseCaseState.Loading` is now redundant (the transition already moved the state).
- Transition resolution is atomic: one loop coroutine, FIFO channel, `processEvent` serialized
  (KStateMachine pending events additionally queue FIFO). This replaces the `scan` guarantee.
- Invalid transition policy: ignore + `AppEvent.InvalidTransition` telemetry (bug-compatible
  with today's silent no-op mutations, but now observable).
- In-flight work is cancelled on state exit (`logging_in.onExit` cancels the sign-in job) —
  previously there was no cancellation policy at all.

## Approved behavior diffs vs. the old implementation

1. **Double `ClickSignIn` while `LoggingIn` no longer re-executes the use case.** Before:
   the mutation no-op'd but the use case ran again (guards protected state, not execution)
   and could navigate twice. Now the event is ignored, telemetry records it, and
   `bootstrapSignIn` runs exactly once (asserted in
   `clickSignIn_whileLoggingIn_isIgnored_andUseCaseRunsOnce`).
   `SignInViewModelContractTest` was adapted accordingly (construction + that one assertion);
   all other assertions are unchanged.
2. `NavigateToSummary` is now emitted by the declared `logging_in × SignInSucceeded`
   transition instead of an unguarded `UseCaseState.Data` branch.

Known smell surfaced (not fixed): `ClickSignIn` carries `(usbId, password)` duplicating what
`Idle` already holds — the transition still reads them from the event for bug-compatibility.

## Library findings

- KStateMachine 0.37.0 resolves for android/iosArm64/iosSimulatorArm64.
- **K2 limitation found:** top-level functions of `kstatemachine-coroutines` (e.g.
  `CoroutineScope.createStateMachine`) are not resolvable from this project (Kotlin 2.4.0,
  AGP 9.2.1 KMP) — both jars declare the same packages and only one module's top-levels win;
  classes resolve fine. Same behavior on 0.36.0. Workaround: machines are created with core's
  `createStdLibStateMachine`, which also confines all listener execution to our machine-loop
  coroutine (stronger serialization, no extra context hops). The `kstatemachine-coroutines`
  dependency stays only as a transitive of core's metadata; revisit if the K2 issue is fixed.
- Export caveat held: only declarative `transition<E> { targetState = ... }` forms are used,
  so the Mermaid export is complete and truthful.
