# Spike: formal state machine behind MVI (SignIn)

Goal: validate that the implicit MVI mutations can be reified as a formal state machine —
transitions as first-class, enumerable entities with validity rules, telemetry, and diagram
export — without touching the screen contract, the UI, or navigation.

The spike ran in two iterations on this branch: first with KStateMachine as the engine,
then replacing it with an owned engine in `base` once the library's real usage surface and
friction were measured. **The owned engine is the final state.** The same oracle test suite
stayed green through both iterations, which is what made the swap a low-risk, evidence-based
decision.

## Final architecture

- `base/presentation/statemachine/`:
  - `TransitionSpec`: one row of the formal table — `from` state class (null = any state),
    `on` event class, declared `to` target class (null = internal transition), and the
    transition function `f: suspend (S, event) -> S`. The mutation is now a named entity.
  - `MachineDefinition`: the introspectable table (`.table`), `process(state, event)`
    returning `Transitioned`/`Rejected`, hierarchical resolution (state-specific rows win
    over machine-level rows), enter/exit actions on state-class change (UML order:
    exit → output → enter), and `exportToMermaid()`.
  - `MachineDefinitionBuilder`: typed DSL. `from<State> { on<Event> { f } }` declares
    internal transitions whose same-class invariant is enforced **at compile time**
    (`(F, E) -> F`); `onTo<Event, Target>` enforces the declared target at compile time
    (`(F, E) -> To`); `fromAny { on<Event> { f } }` declares machine-level transitions
    (runtime-checked same-class invariant). `process` re-validates everything at runtime,
    so even raw `TransitionSpec` construction cannot desynchronize diagram and behavior.
  - `StateMachineViewModel`: same public surface and automatic telemetry as `BaseViewModel`
    (`ScreenView`, `Action`, `State` with name-dedup, `Effect`). A single machine-loop
    coroutine consumes a FIFO channel of inputs; only the loop mutates the `StateFlow`.
    Valid transitions publish `AppEvent.Transition(from, event, to)`; rejected events
    publish `AppEvent.InvalidTransition(from, event)`. User actions are machine events
    directly (`toMachineEvent` defaults to identity) — no event mirror per screen.
- `auth`: `SignInViewModel.defineMachine()` declares the table below;
  `SignInInternalEvent` holds the two use-case results that re-enter the loop.

## The machine (generated by `machine_exportsDeclaredTransitionsToMermaid`)

```mermaid
stateDiagram-v2
state sign_in {
    state idle
    state logging_in

    [*] --> idle
    idle --> idle : SetUsbId
    idle --> idle : SetPassword
    idle --> idle : TogglePasswordVisibility
    idle --> logging_in : ClickSignIn
    logging_in --> logging_in : SignInSucceeded
    logging_in --> idle : SignInFailed
    sign_in --> sign_in : ClickTermsAndConditions
    sign_in --> sign_in : ClickPrivacyPolicy
    sign_in --> sign_in : SetUsageDataCollectionEnabled
}
```

Machine-level self-loops are transitions valid from **any** state, matching today's
unguarded behavior for terms/privacy/consent — declared instead of accidental.

## Semantics (held across both iterations)

- Formal state = the sealed `State` class; payload lives in the instance.
- Inputs = user actions + internal events (use-case results). Launching the use case is an
  output of `idle × ClickSignIn → logging_in`; its result re-enters the loop as an event.
  `UseCaseState.Loading` is redundant (the transition already moved the state).
- Transition resolution is atomic: one loop coroutine, FIFO channel, serialized
  `process` calls. This replaces the `scan` guarantee of `BaseViewModel`.
- Invalid transition policy: ignore + `AppEvent.InvalidTransition` telemetry
  (bug-compatible with the old silent no-op mutations, but observable).
- In-flight work is cancelled on state exit (`from<LoggingIn> { onExit { … } }` cancels the
  sign-in job) — previously there was no cancellation policy at all.

## Approved behavior diffs vs. the old ActionProcessor implementation

1. **Double `ClickSignIn` while `LoggingIn` no longer re-executes the use case.** Before:
   the mutation no-op'd but the use case ran again (guards protected state, not execution)
   and could navigate twice. Now the event is rejected, telemetry records it, and
   `bootstrapSignIn` runs exactly once (asserted in
   `clickSignIn_whileLoggingIn_isIgnored_andUseCaseRunsOnce`).
2. `NavigateToSummary` is emitted by the declared `logging_in × SignInSucceeded` transition
   instead of an unguarded `UseCaseState.Data` branch.

Known smell surfaced (not fixed): `ClickSignIn` carries `(usbId, password)` duplicating
what `Idle` already holds; the transition still reads them from the event for
bug-compatibility.

## Why the engine was swapped (iteration 1 → 2 evidence)

KStateMachine 0.37.0 validated the semantics, but four findings tipped the decision:

1. **Tiny real usage surface**: the glue (FIFO serialization, telemetry, effects,
   lifecycle, cancellation) was ours from the start; from the library we only used the
   lookup, `ProcessingResult`, and export — ~200 lines to own.
2. **Duplicated truth**: library machines hold their own node graph (`idle` nodes) parallel
   to the sealed `State` classes, synchronized only by discipline. The owned engine keys
   the table by the sealed classes themselves and *verifies* `f`'s result against the
   declared target — compile-time via the DSL signatures, runtime in `process`.
3. **Per-screen ceremony**: the library's `Event` marker forced a mirrored event hierarchy
   plus mapping per screen. With class-keyed matching, contract `Action`s are used directly
   and only true internal events need declaring.
4. **K2 dependency wall, day one**: top-level functions of `kstatemachine-coroutines`
   (e.g. `CoroutineScope.createStateMachine`) do not resolve in this project
   (Kotlin 2.4.0 / AGP 9.2.1; both jars declare the same packages and only one module's
   top-levels win — classes resolve, functions don't; same on 0.36.0). Iteration 1 shipped
   on core's `createStdLibStateMachine` as a workaround. A single-maintainer library at the
   architecture core, already off its paved road, decided the swap.

The dependency was fully removed in iteration 2.

## Open items for the real migration (out of spike scope)

- Transition-table validation helper in `testkit` (coverage of the Action alphabet,
  unreachable states) reusable by every screen's machine test.
- Decide per-screen file conventions for `defineMachine()` blocks as tables grow
  (e.g. extract to `presentation/machine/<Screen>Machine.kt`).
- Remove the orphaned SignIn `ActionProcessor`s once the pattern is ratified.
- `@DslMarker` on the builder DSL to prevent receiver leakage between nested blocks.
- README architecture section update when `StateMachineViewModel` becomes the default.
